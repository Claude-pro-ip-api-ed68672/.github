<p>选住宅 IP 平台，多数人先看价格页，结果对接时才发现接口是套壳的、IP 段是云厂商的、账单里还藏着一笔"环境费"。真正做批量开通的人要的其实很朴素：一条带幂等键的请求能拿到整套环境，一个异步回调能知道成没成，一张账单能还原钱花在哪。这篇把平台拆成接入、资源、交付、计费、运维五层，每层给出可以直接拿去问供应商的问题和判定阈值，末尾附一份 7 天试水验收清单，方便按月走接口开之前先摸清底。</p>

<h2>一、把平台拆成五层，先确认自己能吃到哪一层</h2>
<p>五层里任何一层缺失，后面都要靠人力补。最常见的补法是运营同学手工复制粘贴，一天开二十条还行，到了上百条就会开始出错，错的往往还是最难查的那种——IP 和指纹对不上号。所以评估平台的第一步不是比价，是看它把哪几层封成了接口。</p>

<h3>接入层：接口是原生的还是套的壳</h3>
<p>原生接口有三个特征：幂等键、异步任务号、限流响应头。同一个业务单号提交两次，平台应返回同一份环境而不是重复开两条；开通本身是异步的，接口要给你 task_id 供轮询或回调。只有同步返回"成功"、没有任务号、也没有 X-RateLimit 一类响应头的，多半是把控制台操作包了层 HTTP，批量上到五十条就容易超时。</p>

<h3>资源层：地址从哪来，归属查不查得到</h3>
<p>要问的是 ASN 和段类型。自营家宽一般落在 Comcast、Verizon、AT&amp;T 这类运营商 ASN 下；机房段则挂在 AWS、DigitalOcean、Hetzner 一类云厂商 ASN 下。拿到地址自己用 whois 或 ipinfo 查一遍，ASN 写着云厂商的直接退。还要问同一个 /24 里已经卖出多少条，这个数字决定同段关联的概率。</p>

<h3>交付层：给的是地址还是整套环境</h3>
<p>只回 IP、端口、账号、密码的，时区、语言、字体、WebRTC 全要自己对齐；给整套环境的，通常返回一个 profile 包，含 UA、分辨率、字体清单和 DNS 出口。长期登录同一账号的场景，后者能省掉大量排查——环境不一致带来的异常提示，比线路抖动难定位得多。</p>

<h3>先拿 5 条量跑通全链路</h3>
<p>联调阶段不要直接上量。5 条足够覆盖正常、余额不足、地区售罄、参数非法四种返回，把这四条分支的错误码记下来写进自己的重试策略，后面才不会出现"平台提示失败、实际已开通"的重复计费。</p>

<h3>失败重试要有退避，不要裸循环</h3>
<p>批量任务最常见的自伤是失败即重试，一秒一次打满对方限流。建议指数退避，1、2、4、8、16 秒，累计 5 次仍失败转人工；同时把 request_id 一起带上，避免对方按请求次数计费时多扣。</p>

<h3>把停机天数折进单价再比</h3>
<p>算实际单价的公式是：月费 ÷（30 − 预计停机天数）。旺季满跑、淡季停一半的账号，年付折算下来往往比按月贵。反过来，全年不缩量的场景，年付确实能省，但要先确认合同里有没有"停用不退款"和"换线不计费"两条。</p>

<h3>换线、换地区算不算二次收费</h3>
<p>这一条最容易被忽略。线路不通要求更换时，有的平台按新开计费，有的免费换但只换同城。问清楚三个点：免费换线的次数上限、是否限制同城、故障判定以谁的检测为准。自营线路通常敢写"换到可用为止"，转售线路多半只能换一次。</p>

<h2>四、7 天试水怎么验收，别只看通不通</h2>
<p>试水的目的不是验证"能连上"，而是验证"连上之后稳不稳、账单对不对"。建议按天分任务：第 1 天看接口连通与错误码，第 2 到 3 天看长连接稳定性，第 4 天查段归属，第 5 天对账，第 6 到 7 天压一次小批量并发。</p>

<h3>稳定性看抖动不看均值</h3>
<p>平均延迟好看没用，要看 P95 和断连次数。做法很简单：对同一地址连续 ping 与 curl 各 200 次，记录 P50、P95、丢包率和断连次数。住宅线路 P95 高于均值两倍属正常，但 12 小时内断连超过 3 次就要问是不是共享段。</p>

<h3>对账要能对上每一分钱</h3>
<p>把平台的用量明细和自己的开通记录按 request_id 做一次全量比对，重点看三类差异：开通了但没记录、记录了但没开通、同一条被计两次。差异率超过 1% 就别急着放量，先让对方出明细解释。</p>

<h2>常见问答</h2>

<h3>按月走接口开，比一次性买年付贵多少？</h3>
<p>答：通常贵 15% 到 30%，但只对全年满跑的场景成立。按 30 天里平均停 8 天算，月付的总支出反而常常低于年付，因为年付的停机天数不退款。先按自己过去三个月的实际在线天数估算，再决定要不要锁年。</p>

<h3>API 支持批量，是不是就不用管并发限制了？</h3>
<p>答：不是。批量接口一般有每秒请求数和单次提交条数两个上限，超出会返回 429。正确的做法是客户端自己排队，队列长度按对方限流值配，不要把重试压力全丢给服务端，否则容易出现部分成功、部分重复的中间态。</p>

<h3>平台给的 IP 怎么快速判断是不是机房段？</h3>
<p>答：取地址后查 whois 的 orgname 和 ASN。orgname 出现 Amazon、Google、DigitalOcean、Hetzner、OVH 这类字样的基本可判定为机房；再查该段的 abuse 记录数量，短期内有大量投诉的段，纯净度通常不好。</p>

<h3>试水期只开 5 条，能看出线路稳不稳定吗？</h3>
<p>答：能看出明显问题，看不出长期趋势。5 条跑 7 天，足以暴露开通失败、段归属错误、账单口径不一致这三类硬伤；但晚高峰抖动和同段关联要拉长到 3 周才明显。所以试水通过后，第一次放量建议不超过总量的三成。</p>
